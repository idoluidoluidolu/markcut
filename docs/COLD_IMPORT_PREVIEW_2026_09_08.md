# 初次匯入與拖曳預覽修正（2026-09-08）

本輪基於 `3be374a`，處理使用者提供的 iOS `1.1.0+194` 五支影片疊軌診斷。改善目標是選完素材後更早辨識、操作，以及減少拖曳定位等待；不是承諾任何大小的素材都能一秒下載、轉檔或精準解碼。

## 報告能確認的事

- 五支影片都是從時間軸 0 秒起疊放，來源為 2160×3840 HEVC、約 30fps、HLG HDR；最長一支約 48.38 秒。
- HDR 代理背景準備約 26 秒，最長片段先轉，單支約 16.2 秒。記憶體峰值 1119MB。
- 合成共重建四次；初段要求多條來源軌。報告出現來源供格相隔約 370ms、扣除影片時間前進後額外等待約 337ms。這是需要減少同時解碼工作的證據，不能單憑它判定所有卡頓都是同一原因。
- 樣式更新平均約 23ms，最大約 30ms；本輪優先處理解碼、縮圖排程與定位收尾。
- 舊報告「畫面 297 張、87 張／秒」來自共用 CI 完成計數，會包含背景代理轉檔，不是螢幕呈現 FPS。不能用這個數字宣稱拖曳已順。
- 起播的 401／416ms 沒有位置前進確認事件，屬於約 400ms 的確認逾時，不能當成實測首幀延遲。
- 「工作檔 0 支」只數 SDR 路徑，漏算了已備好的 HLG 代理。
- 音訊 session 啟用到首度合成之間另有未分段量測的時間。現有報告無法分辨相簿匯出、檔案搬移、中繼資料或 iCloud 下載各花多久。

## 本輪改動

### 減少預覽需要的來源

iOS 建立預覽合成指令時，若已查證一支不含 alpha 的影片完全、不透明地覆蓋畫布，略去它下方的圖層，並從必要來源軌清單移除。音軌保持原樣。圖片、GIF、馬賽克不作為遮蔽判據；淡入淡出、裁切、自由旋轉、透明度、未知 alpha 等情況保守保留。

使用反向座標檢查畫布四角，而非只比較旋轉後的包圍盒。使用者首次調整片段大小、位置、旋轉或透明度前，恢復完整來源，直到正式重建，避免露出下層時變黑。

預熱改為真正的交界前 1.5 秒區間，避免用整條指令的末端計算而讓下一支解碼器提早數十秒常駐。診斷新增每段需要的來源軌數。

Apple 的 [requiredSourceTrackIDs](https://developer.apple.com/documentation/avfoundation/avvideocompositioninstructionprotocol/requiredsourcetrackids) 定義了自訂合成指令所需來源。此處減少的是預覽必要來源，不更動匯出原檔或 HDR 轉換數學。實際節省的解碼量、記憶體與延遲仍須手機量測。

### 拖曳中快速定位，停手後確認落點

原檔尚未換上代理時，拖曳定位允許最多 150ms 時間容差；代理與停手精準定位仍為零容差。維持只追最新目標的 seek 排程。Apple 的 [QA1820](https://developer.apple.com/library/archive/qa/qa1820/_index.html) 說明了快速連續 seek 互相取消的問題。

新增原生定位完成收據。Dart 在精準定位完成前保留拖曳快取；新手勢、播放、重建或離頁作廢舊收據，舊完成事件不能撤掉新手勢的快取。片尾重播也必須先等歸零定位成功再播放。

原檔抽幀容差從整支影片長度收斂至最多 250ms。AVAssetImageGenerator 的容差不是「必定回傳最近關鍵幀」保證；本輪補回 iOS actualTime，以真實取樣時間判斷快取是否適合目前位置。舊原生／Android 沒提供時間的結果明確保留為未知，不假造為請求時間。最終落點仍交給精準 seek。

### 重用抽幀器並減少被遮蔽素材的快取工作

使用者追問更根本的處理後，查到原本只有 AVURLAsset 快取，每張圖仍重新建立 AVAssetImageGenerator。本輪改成最多兩顆抽幀器的 LRU 池，由既有序列佇列獨占存取；按路徑、檔案大小、修改時間及輸出尺寸辨識。同路徑內容更換後淘汰舊抽幀器，並在記憶體警告、退背景、播放器銷毀與編輯器離頁時釋放。每張圖使用 autoreleasepool，限制中間物件累積。

這是重用 AVFoundation 抽幀器，不代表 API 保證硬體解碼器永久常駐。既有 JPEG 編碼及 HDR 粗覽色調映射仍存在，尚未改成全程 GPU 紋理輸出。

原生回報本次合成已確認不透明的素材路徑。Dart 抽幀候選與快取就緒判定共用保守規則：只有最上層影片確定全覆蓋、不透明、沒有變形／混合效果時才只服務該支。不能只剔除請求卻繼續等待下層快取；也不能根據 `.mov`／`.mp4` 副檔名猜測 alpha。

### 每支先有封面，再補完整縮圖

播放頭附近、上層素材優先各取一張 0 秒附近、200px 的封面，不再為每支封面先等 600ms。所有素材嘗試取得封面後，再於閒置期間補完整縮圖帶。

播放及匯出時不開始新封面；完整縮圖逐格檢查互動狀態，讓後續抽幀暫停。已開始的原生請求仍會完成。換檔或移除素材後回來的舊圖不得覆蓋現有素材。

### 可比較的診斷

起播統計改稱「起播到位置前進」，不冒稱首幀呈現；未確認前進的逾時獨立計數，不納入平均。拖曳報告分開列 seek 完成量與 CI 完成量，明示 CI 含背景工作、不換算螢幕幀率。SDR 工作檔與 HDR 代理分開記帳。另列出抽幀器的建立／重用次數，並補上進場 HDR 分類與首合成時間，明確排除選取器和相簿取檔時間。

## 驗證與限制

最終完整 Flutter 回歸：**823 項通過，7 項需額外啟用的效能測試跳過**，包含既有畫面快照及設定 `MARKCUT_FFMPEG` 後的真實 GIF 像素輸出驗證。`dart analyze --format machine lib test integration_test` 無問題，`git diff --check` 通過。

完整測試初跑發現匯入順序測試仍掛著編輯頁卻要求背景排程全部結束；修正為明確離頁後再排空有限等待，確認不續排，完整重跑全數通過。沒有為此停用背景功能或略過測試。

新增 **10 項 Swift XCTest** 涵蓋抽幀器重用／失效、遮蔽幾何、保守保留、預熱窗口、編輯恢復及定位收據；Windows 環境沒有 iOS SDK，尚未執行原生編譯或 XCTest。

驗證使用本機 Flutter runtime，指令為 `flutter test --no-pub --no-test-assets`。`--no-test-assets` 避開此 Windows 環境既有著色器編譯器問題，不代表手機 GPU 已驗證。

本輪未改整支 HDR 代理轉檔的編碼速度，也未把所有素材的背景準備改為區段代理。大量 4K 長 GOP、iCloud 未下載素材或多層真正同時可見時，仍有不可忽略的讀取及解碼成本。沒有本輪真機前後對照，不能宣稱已達到秒匯入或固定 FPS。

更完整的預覽核心仍須處理三件事：以原生像素緩衝／GPU 紋理取代 JPEG 往返，讓原檔和代理共用相同 HDR 合成；以播放頭附近的短區段取代整支代理的就緒依賴；將素材接入、合成準備與 UI 可操作時間分開排程。這些是後續架構工作，不是本輪已完成項目，也無法由外觀推斷 Edits 的內部實作。

## 上機對照

使用同一台手機、同一批本機素材，關閉 App 後重新匯入，分開記錄選取器關閉到可操作、各軌封面出現、背景代理完成。進場立刻快速左右拖動、停手、再次拖動並立即播放，確認不閃回舊格，也不被舊定位結果卡住。

在五軌重疊起點檢查診斷的必要來源軌數，移到上層結束交界確認下層如期出現。再縮小／移走上層、調低透明度，確認下層即時恢復。HDR 色彩與匯出仍需在真機確認，螢幕錄影及截圖的色調映射不能替代 HDR 像素驗證。
