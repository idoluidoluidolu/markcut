> 記錄「預覽畫面」這條線的最終架構、已定罪的根因、以及三條紀律。

## 2026-09-05：圖片透明度與額外變暗修正

後續回報：圖片透明度 100% 仍偏色，因此透明度修正不能解釋完整現象。追查發現 `MCStillLoader` 僅以中灰 HLG 碼 <0.407 分類，會把「顯示參考但白基準偏低」誤判成場景參考，且完全未校正白基準。改以白色／中灰比值辨識曲線，獨立計算 RGB 白基準增益，使 SDR 白對齊 0.75 HLG；校正後兩個樣本都驗證通過才快取。預覽與匯出共用載入器，SDR 輸出不進此校正。原生新增 100% 不透明 PNG 載入／HLG 像素測試與六種曲線／白基準組合測試；此 Windows 環境無 Swift／iOS SDK，尚未執行，不能據此宣稱實機偏色已消失。

- 圖片調整面板的透明度跟位置、縮放一起送 `setXform`；原生在原圖層套絕對透明度，再乘片段淡入淡出。透明度不再觸發 Flutter 圖片補畫，避免覆蓋已合成的浮水印。
- 面板滑桿按住時延後重建；合成上屏通知與 1.7 秒清理都檢查更新版本，不能清掉較新的即時值。
- CIColorMatrix 的色彩調整使用非預乘 RGB；透明度只改 alpha，移除原本同時乘 RGB 的額外壓暗。共用 CI 合成器的預覽與匯出一併修正。
- 新增滑桿數值與延遲清理回歸驗證，以及 iOS 像素測試（白疊白不變灰、彩色以正確比例混合）。Windows 無法執行 iOS 像素測試，原生編譯與實機色彩仍須在 Mac／iPhone 驗證。

## 2026-09-05：預設先進編輯、背景準備

使用者重新指定「盡快匯入且可拖曳編輯」，取代下方第 5 節原先的等待要求。

- `VideoEditorScreen.waitForPreparation` 預設 `false`：先讀中繼資料、判定 HDR 並建立初始播放器，不等整支工作檔與完整縮圖帶。`true` 保留原有等待流程供相容測試。
- 工作檔仍串行編碼；每支開始前等編輯器閒置，整批完成後於停止播放／拖曳／捏合／浮水印手勢時換檔。已開始的硬體轉檔不會在手勢起手時中止。
- 一般拖曳不再從開頭用 FFmpeg 掃整條影片。`ScrubFrameQueue` 只排目前可見素材的目標格，再補前後各一格，單一解碼請求在途；跳位會替換待辦，重複格重用快取。簡易倒轉仍保留密集抽幀。
- 速覽抽幀使用 540 長邊，放手沿用精準定位。變更的是拖曳預覽，未調降工作檔或匯出的解析度設定。
- 過期結果只可補快取，不能蓋掉新位置；播放、匯出、換檔與離頁會作廢待辦。抽幀無結果時回退播放器，避免等到放手才更新。
- 原檔／代理的判定跟隨已建立的合成播放器，不因背景剛寫入新工作檔路徑就提早切換。
- 背景準備期間先補每支一張縮圖，完整縮圖帶與換檔後更新併批且等待閒置。

驗證：`scrub_frame_queue_test` 覆蓋快速跳位、單一在途、多層順序、重複请求、播放與離頁失效；`import_eta_gate_test` 用不完成的轉檔工作驗證時間軸可操作，並保留原等待模式測試。另回歸匯入順序、手勢重繪、探測快取和工作檔快篩。

Windows 環境的既有 `mosaic.frag` 著色器編譯器崩潰，因此邏輯／widget 測試使用 `flutter test --no-pub --no-test-assets ...`；不代表已通過完整圖形建置或手機效能驗證。相簿選取器先複製檔案、iCloud 下載，以及首次讀取 4K／HDR 疏關鍵幀的解碼時間仍然存在。後续若實機仍卡，需以實際素材量測冷匯入到可操作時間、拖曳延遲和播放掉格，再評估分段代理或原生編碼暫停排程。

## 0. 三條紀律（來自外部架構體檢，已採納）

1. **一個畫面一個畫家**：畫面永遠只有系統 AVPlayer（合成播放器）。任何「上台/下台/讓位/回台」都是債。
2. **改樣式不准碰解碼器**：暫停中改樣式＝換一份新的 videoComposition 原地重畫（`CompPlayer.rerenderPaused`），不做假 seek。
3. **主執行緒不搬大位元組**：疊圖只烘元素外框（典型文字 ~240KB），不烘整張畫布。

## 1. 最終架構

- **播放**：AVPlayer(AVMutableComposition) + 自訂 CoreImage 合成器（預覽＝匯出同一顆、同一套 HLG 夾白/×3 數學）
- **暫停**：播放器停格（零換手）
- **滑動**：播放器 seek（代理轉正＋密關鍵幀後單軌 1~9ms）；放手一發精確 seek
- **樣式/幾何**：`lib/services/overlay_sync.dart` 狀態機——最新版直烘、單一在途、序號丟舊、80ms 節拍、靜默 500ms 一次全解析 → `setOverlays` → 原生換 vc 重畫
- **Metal 引擎**：合成在場時永不上台、永不預建（`_metalPrebuild` 第一行 `if (_compOn) return`）；只剩匯出/取樣用途
- **代理**：HDR 代理走 HDR 合成器烘正（方向烘死、HLG 標記寫檔、不動色調）；快取鍵 `#hdr6`

## 2. 團隊定罪的根因（我自己 100+ 版沒看到的）

| 症狀 | 真根 | 修法 |
| --- | --- | --- |
| 方向反了 | hdrPass 的旋轉合成器是死碼：純軌道輸出＋Resize 拉伸＝中繼資料完美、像素橫躺變形 | 統一走 `AVAssetReaderVideoCompositionOutput`、去 Resize、去 writer transform |
| 樣式閃爍（新→舊→新） | 合成器缺格時重播「含舊樣式的整格」 | `lastComposedBase`（不含疊加物）＋當下樣式重畫 |
| 樣式卡頓 | 每版兩發精準 seek＋預捲轟暫停中的 10-bit 解碼器 | 刪冗餘 seek、疊圖驅動後不預捲、最後改為換 vc 重畫 |
| 重建閃第 0 格 | 圖層一就緒就翻面，對位 seek 還沒落地 | `PlayerHosts.hold/release`：seek 落地才翻 |
| 每支代理一次重建 | 指紋含路徑＋存草稿計時器逐支觸發 | 整批一次 |
| 閃退風險 | 合成器統計無鎖被兩條佇列同時改 | `slowLock` |
| 陰影/粗細不對 | 畫家數學：描邊雙層透明度管壁、陰影透進字內、像素常數 | 單一群組透明度、字級尺度 |

## 3. 診斷報告判讀

| 欄位 | 意義 |
| --- | --- |
| 交格亮度 `…源亮X` | 輸出黑而源亮＝CI 染黑；源也黑＝解碼器交黑 |
| 催重畫 `N發/丟M/換件K次/vc換N延M` | vc換 應取代 發；換件應只在真正重建 |
| 拖曳 seek 平均/九成 | 單軌 <10ms、多軌 <40ms 為健康 |
| 浮水印管線 改變到上屏 | 九成 <100ms 為即時 |
| 互動事件流 | 上台/讓位/重建/斷流/卡格毫秒時間線；「引擎上台」在合成模式應為 0 |
| 軌道幾何 | 轉正代理應為 `WxH@0°`；出現 90° 即雙重旋轉 |

## 4. 工作法教訓

- 探針量中繼資料 ≠ 量像素；YDIF 靜止 ≠ 凍結（暫停畫面本來就不動）
- 同一症狀常是多個互餵機制；單修任一都「一樣」
- 卡死時派**乾淨上下文**的獨立審查者（不給既有理論、不信註解），一輪即定罪
- Swift 無編譯器：每批改動派「逐行審查員」當編譯器，通過才 build
- 測試素材必須踩使用者必經路徑（有聲＋HDR＋旋轉＋觸發轉檔）
